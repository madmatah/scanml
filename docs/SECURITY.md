# Security — threat model and guarantees

## What we protect against

The OCR engine (PaddlePaddle, PaddleOCR/PaddleX, vLLM and the model code
downloaded from Hugging Face) is treated as **untrusted**. Working assumption:
this code might try to read secrets (SSH keys, tokens, browser data…), to
exfiltrate them, to settle permanently on the machine, or to slip booby-trapped
content into its results.

## Guarantees of the `ocr` sandbox

| Measure | Effect |
|---|---|
| `network_mode: none` | no network interface except `lo`: no DNS, no Internet, no LAN, no access to the host over the network |
| no mount of `$HOME` | the only visible paths: `/opt/sandbox` (venvs + models, **read-only**), `/run/scanmylib` (the socket), `/var/cache/ocr` (compilation cache), `/tmp` (tmpfs in RAM) |
| `read_only: true` | the container's file system is read-only |
| `cap_drop: [ALL]` + `no-new-privileges` | no Linux capability, no escalation through setuid |
| non-root user (uid 1000 in the container) | no root privileges in the container |
| `pids_limit`, `mem_limit: 16g`, `shm_size`, bounded tmpfs | resource limits (processes, RAM) |
| rotated Docker logs (5 × 10 MB) | the sandbox cannot fill the system disk by writing logs |
| GPU through CDI only | the only device exposed |

Downloads (packages, models) are made **only once** by `ocr-setup`, which has
network access but only sees `SANDBOX_DIR`. Pinned versions:
`paddlepaddle-gpu==3.2.1`, `paddleocr==3.7.0`, `vllm==0.31.0`, and the models
by Hugging Face commit (see `ocr/setup/install.sh`, `SANDBOX_DIR/MANIFEST.json`).
No Paddle code runs during this network phase: the models are fetched with
`huggingface_hub`.

The script `scripts/verify-sandbox.sh` (53 checks) verifies these properties on
the running container (network interfaces, DNS resolution, outbound
connections, visible files, capabilities, read-only file system).

## OCR results are untrusted data (`api` side)

Rules applied by the api to every answer of the sandbox:

- **Bounded sizes**: response ≤ 128 MiB, Markdown ≤ 2 MiB, block text ≤ 2 M characters per page, ≤ 64 images per page, ≤ 20 MiB per decoded image, dimensions ≤ 12,000 px. Answers of `/health` are limited to 64 KiB, and `/api/status` only relays typed and bounded fields.
- **File names**: only names matching `[A-Za-z0-9._-]{1,128}` without `..` are accepted; the files written to disk are named by the api (`images/<key>_<n>.jpg`), never with the name provided.
- **Images re-encoded** with Pillow (JPEG): nothing but pixels reaches the disk.
- **Markdown sanitized** before it is written: tags are rebuilt from scratch, and only an allowlist of formatting tags and attributes survives; script-like elements (`script`, `style`, `iframe`, `object`, `svg`, `math`, `template`, `textarea`, `select`…) are removed with their content, other tags (`embed`, `link`, `meta`, `base`, `form`, `input`, `button`…) without it; no `on*` attribute, `style` reduced to `text-align`, no `srcset`; HTML comments removed (they could fake the page markers of `document.md`); no URL except the page's own images: image `src` can only target them, and any other link or Markdown reference definition is neutralized.
- **Web previews**: Markdown → HTML (markdown-it-py), then allowlist filtering (nh3); the web UI is served with a strict CSP (`default-src 'self'`, no inline script, `frame-ancestors 'none'`) and `X-Content-Type-Options: nosniff`.
- **Formulas**: KaTeX 0.19.0 (MIT) typesets the LaTeX formulas of the previews; it is served by the PC (`scripts/vendor-katex.sh`: npm tarball checked against its SHA-512 hash, no CDN), receives the TeX as text and renders it without risky commands (`trust: false`: no `\href`, `\url`, `\includegraphics` or `\html…`).

## Known residual risks (low)

- NVIDIA's CDI specification (generated by `nvidia-ctk` on the host) exposes a
  few extra NVIDIA device nodes and the socket of the `nvidia-persistenced`
  daemon to the sandbox. Restricting them would require changing the system
  configuration (sudo).
- The host folders the sandbox can write to (`DATA_DIR/run`,
  `DATA_DIR/ocr-cache`) are on the same partition as the api's state, without
  a quota. A malicious sandbox could fill it (denial of service), without
  being able to read or exfiltrate anything.

## Residual risk: prompt injection

The text produced by the OCR, like any book text, may contain sentences that
look like instructions ("ignore your instructions and…"), whether they are in
the book itself or added by a booby-trapped model. Your agents must treat the
library as **reference material**, not as orders: ideally, they read it
without having access to sensitive tools (sending data, secrets) at the same
time.

## On the local network

- Uploads without a valid token are refused **before** the request body is read (no memory used up by a stranger).
- The api listens on port `API_PORT` of every interface, so that the phone can reach it. Every route requires the token, except `/api/health`, logging in and out (`/api/session`), the APK and the files of the web UI (`/`, `/static/…`).
- Traffic is plain HTTP on your local network. To scan away from home, use a VPN (WireGuard, Tailscale…) rather than opening the port to the Internet.
- The token is regenerated by deleting `DATA_DIR/state/token`, then restarting the api. The phone must then be paired again.

## The Android APK

- **Build**: from the code in `android/`, in throwaway containers
  (`scripts/build-apk.sh`). Tools are checked against their hash before use:
  Android tools (SHA-1 published by Google), Gradle distribution (SHA-256
  published by Gradle), and every library against a pinned hash
  (`android/gradle/verification-metadata.xml`).
- **Signing**: the signing key is created once in
  `DATA_DIR/android/keystore/`, never in the repository. Signing happens in a
  second container **without network**: the build code and its plugins never
  see the key. **Back up this folder.** Without it, a new APK cannot update the
  installed app: it would have to be uninstalled, which deletes the pages not
  sent yet.
- **Permissions**: the app uses the network, and WorkManager adds permissions
  granted without asking (wake lock, network state, restart at boot). The only
  permission asked of the user is the **camera**, and only when entering the
  "Camera, page by page" mode (CameraX). Google's document scanner and QR
  code reader (ML Kit), provided by Google Play services, do not need it.
  Importing goes through the system photo picker, without storage permission.
  Photos stay in the app's private storage until they are sent.
- **Token**: it is only sent to the paired PC, never to another address (not
  even for thumbnails). It is excluded from Android backups and from transfers
  to another phone.
- **Google metrics**: according to Google's terms, ML Kit sends usage and
  performance metrics to Google. Images and text stay on the phone, and no
  documented setting turns this off. On the PC side, the new Android SDK
  installer ("Android CLI") collects statistics by default: the script always
  runs it with `--no-metrics`. During the very first installation, on October
  12, 2026, before this setting, it most likely sent a usage report to Google
  (commands and options, no files).
